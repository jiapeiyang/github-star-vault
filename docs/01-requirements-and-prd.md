# 需求与产品方案

## 1. 问题定义

当前动作很顺：在 GitHub 看到有价值的项目，点击 Star。问题发生在收藏之后。

GitHub 原生 Stars 页面能按最近收藏、最近活跃、Stars 数排序，也能按语言和仓库类型过滤，还提供公开 Lists。但它仍然缺少几类与个人学习直接相关的信息：为什么收藏、准备怎么用、是否已经读过或跑过、与哪些项目类似、个人结论是什么。官方搜索主要面向仓库名与 Topic，也无法按个人备注找回项目。

所以需求不是“复制一个更好看的 Stars 页面”，而是完成下面的转化：

> 随手收藏 → 自动进入收件箱 → 低成本整理 → 需要时找回 → 进入学习或实践 → 留下可复用结论。

## 2. 产品目标

### 2.1 核心目标

- 保持现有 Star 习惯，不要求换收藏入口。
- 新 Star 自动进入知识库，避免再次成为无人处理的历史库存。
- 用低成本字段表达个人判断，而不是重复 GitHub 的公开元数据。
- 通过搜索和多维筛选，在 30 秒内找回一个记不清名字的仓库。
- 把一部分收藏推进到真实学习，留下最低限度的学习证据。
- 同一份数据同时生成 GitHub README 和公开静态网站。

### 2.2 成功不是“收录更多”

项目是否成功应由这些指标判断：

- 新收藏 7 天内整理率。
- 历史待整理库存每月减少量。
- 每月被重新打开的旧项目数。
- 从 `queued` 或 `learning` 进入 `learned` 的项目数。
- `learned` 但没有 `takeaways` 的数量，目标始终为 0。
- 典型检索任务能否在 30 秒内完成。

Stars 总数和网站访问量可以展示，但不能证明“吃灰”问题被解决。

## 3. 用户与公开边界

### 3.1 主用户

仓库所有者本人，同时扮演收藏者、整理者和学习者。所有写操作先通过 Git 文件完成，不做后台管理系统。

### 3.2 次要用户

公开网站的访问者。他们可以浏览项目和个人推荐理由，但不能修改内容。

### 3.3 MVP 默认边界

- GitHub 仓库与网站公开。
- 只同步公开 Stars。
- 个人注释也会公开，不写入公司内部信息、令牌、账号或其他敏感内容。
- 网站只读，无登录、注册、评论或多用户权限。
- 中文是主要界面语言，仓库名、官方描述、命令和技术名保留原文。

## 4. 核心用户旅程

### 4.1 收藏与自动进入收件箱

1. 用户继续在 GitHub 点击 Star。
2. GitHub Actions 每 6 小时读取一次公开 Stars，也允许手动运行。
3. 新发现的仓库进入 `inbox`，页面显示收藏时间与最近成功同步时间。
4. 取消 Star 的仓库退出默认列表；已经写过的个人内容继续保留。

验收口径：在一次成功同步后的构建中出现，不把定时任务的计划时间当作成功证据。

### 4.2 低成本整理

处理一个新 Star 时只要求完成四个选择：

1. 一个主分类：它属于哪个领域。
2. 一个资源类型：它是什么形态。
3. 一句话价值：它对我有什么用。
4. 一个学习阶段：接下来准备怎么处理。

个人标签可选，最多 5 个。第一版不要求星级评分、长摘要、成熟度打分或完整读后感。

### 4.3 搜索与找回

项目库搜索覆盖：

- 仓库名、owner、官方描述。
- GitHub Topics。
- 个人主分类、资源类型和标签。
- 一句话价值、个人笔记和学习结论。

筛选支持：主分类、资源类型、语言、学习阶段、个人标签、上游是否 archived。排序支持：最近收藏、最近更新、Stars 数。

筛选状态写入 URL 查询参数，方便保存和分享。

### 4.4 从收藏进入学习

1. 把值得投入时间的项目设为 `queued`。
2. 真正开始读 README、运行项目或在工作中试用时设为 `learning`。
3. 写下至少一条 `takeaway` 后才能设为 `learned`。
4. 实践链接、命令、截图或详细笔记可选，后续有真实需求再扩充。

使用“已学习”而不是“已掌握”。仓库持续变化，“已掌握”会制造不必要的完成感。

### 4.5 每周整理与每月回顾

每周入口聚焦：本周新收藏、仍未整理的新项目、当前学习中项目。

每月入口聚焦：历史待整理、长期未处理、上游已归档、随机重访一个旧收藏。

第一版不实现间隔重复算法。先验证用户是否会使用回顾入口。

## 5. 分类体系

主分类回答“哪个领域”，资源类型回答“什么形态”，语言与 GitHub Topics 仅作为自动筛选维度。

### 5.1 建议主分类

| ID | 展示名 | 典型内容 |
|---|---|---|
| `ai-agent` | AI 与 Agent | LLM、Agent、Claude Code、Codex、MCP、Skills |
| `web-client` | Web、前端与跨端 | React、Vue、浏览器、跨端应用 |
| `backend-data` | 后端与数据 | API、数据库、服务端框架、数据工程 |
| `infra-security` | 基础设施、网络与安全 | 云原生、网络、自托管、安全工具 |
| `devtools-automation` | 开发者工具与自动化 | CLI、IDE、终端、自动化与工程效率 |
| `design-content` | 设计、图像与内容创作 | UI、图像、视频、写作与演示 |
| `cs-engineering` | 计算机基础与工程实践 | 算法、面试、架构、工程教程 |
| `business-domain` | 商业与行业应用 | 金融、增长、行业解决方案 |

无法判断时保留 `unclassified`。不设置含义模糊的“其他”来掩盖分类问题。

### 5.2 建议资源类型

- `app`：应用或工具。
- `library`：库或框架。
- `template`：模板或脚手架。
- `learning`：教程、书籍或课程。
- `collection`：Awesome List、资料合集或数据集。
- `research`：研究、示例或实验项目。

### 5.3 约束

- 每个仓库最多一个主分类。
- 一个仓库可有多个个人标签，最多 5 个。
- 不把 `JavaScript`、`Python` 等已有语言字段重复写入个人标签。
- GitHub Topics 原样保存，但不当作人工确认的分类。
- 功能相似的仓库通过 `related` 或专题集合关联，不自动合并。
- 机器建议和人工确认必须能区分；人工确认后自动任务不可覆盖。

## 6. 学习阶段

| 值 | 展示名 | 定义 |
|---|---|---|
| `imported` | 历史待整理 | 首次导入的旧 Stars，尚未人工确认 |
| `inbox` | 新收藏 | 系统上线后新增，尚未整理 |
| `queued` | 待学习 | 已确认值得投入时间 |
| `learning` | 学习中 | 正在阅读、试用或实践 |
| `learned` | 已学习 | 已留下至少一条个人结论 |
| `reference` | 仅参考 | 有需要时查询，不安排系统学习 |
| `archived` | 已归档 | 当前不再关注，默认隐藏 |

上游仓库的 `github_archived=true` 与个人 `stage=archived` 是两个概念，必须分别显示。

## 7. 初始化迁移

283 个历史项目不能全部进入“新收藏”，否则上线当天就产生无法处理的收件箱。

建议流程：

1. 全量导入，全部历史记录初始化为 `imported`。
2. 根据仓库名、描述、Topics 生成一次性分类建议，标记为“待确认”。
3. 先人工整理最近 30-50 个，以及现在确实想学的项目。
4. 此后每个新 Star 尽量在 7 天内处理。
5. 每周额外整理 5-10 个历史项目，不设一次性清零目标。

## 8. 网站信息架构

### 首页

首页首屏回答三件事：最近收了什么、现在学什么、以前有什么值得重看。

- 总 Stars、已整理、待学习数量。
- 最后成功同步时间。
- 继续学习入口。
- 新收藏与最近新增。
- 主分类入口。
- 随机重访。
- 最近完成的学习记录。

### 项目库

- 紧凑列表为默认视图，卡片视图可选。
- 全文搜索和组合筛选。
- 清晰展示结果数量、激活的筛选条件和清除入口。
- 上游 archived 仓库默认不隐藏，但带明显标识；个人归档默认隐藏。

### 仓库详情

- GitHub 官方事实：名称、描述、语言、Topics、License、Stars、最近更新。
- 个人判断：一句话价值、主分类、类型、标签、学习阶段。
- 时间：收藏时间、上游更新时间、最近同步时间、个人更新时间。
- 学习结论与相关项目。
- GitHub、homepage 和个人实践记录链接。

### 学习页

- 当前学习中。
- 待学习队列。
- 已学习历史。
- 历史待整理进度。
- 仅参考资源。

MVP 可把分类页和学习页实现为项目库的预设筛选 URL，减少页面和路由数量。

### 关于页

说明项目目的、分类和状态定义、数据来源、更新时间，以及哪些字段来自 GitHub、哪些是个人判断。

## 9. MVP 范围

### 必须完成

- 导入全部公开 Stars。
- 每 6 小时自动同步，并支持手动触发。
- 用 `repo_id` 去重并处理仓库改名。
- 人工内容与生成内容隔离。
- 生成 README 分类索引。
- 构建首页、项目库、仓库详情、关于页。
- 搜索官方元数据与个人内容。
- 按分类、类型、语言和阶段筛选。
- 显示最后成功同步时间。
- 正确区分取消 Star、上游归档和个人归档。

### 第二阶段

- 学习页、每周整理和每月回顾。
- Takeaways 完成约束。
- 相关与替代项目。
- 仓库归档、长期不更新等变化提示。
- 可选的 GitHub Issue 周报。

### 有使用证据后再决定

- AI 分类、摘要和相似项目建议。
- 语义搜索与自然语言问答。
- 浏览器快捷入口或秒级同步。
- 私人笔记与公开站点分层。
- 在线编辑后台。
- 专题合集、订阅与自定义域名。

## 10. 明确不做

- 不做多用户、账号、评论和社交关系。
- 不把数据库或 SaaS 管理台引入 MVP。
- 不自动取消 GitHub Star，也不自动永久删除个人笔记。
- 不强制给 283 个历史项目补齐长摘要和评分。
- 不定时抓取全部仓库的完整 README 或源码。
- 不自动采信 AI 分类。
- 不把私有仓库信息写入公开构建产物。
