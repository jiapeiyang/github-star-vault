## 它是什么
Flux Comparison 用同一个小型购物车应用展示多种 Flux 相关状态管理实现。它把界面任务尽量保持一致，让读者比较状态存放位置、动作如何分发，以及购物车更新如何传到视图。

它的价值是横向对照：一个实现的概念可能难以单独理解，但把相同的“加入商品—购物车变化—结算载荷”放在多套代码里看，就更容易识别它们的共同点和差异。仓库包含 Facebook Flux、Redux、Reflux 等实现目录。

## 适合什么场景
- 回顾 React 生态早期状态管理的演变。
- 阅读旧项目时遇到 dispatcher、store、action 等概念，需要一个较小的对照应用。
- 想比较同一业务动作在不同实现中的调用链，而不是只比较库名和宣传介绍。

这是一组历史示例，不是今天选择状态管理方案的实时排行榜，也不代表所列项目都仍在维护。

## 如何开始
1. 阅读 README 的 Examples 列表，选择两种希望比较的实现。
2. 获取仓库后先阅读根目录与实现目录的 package.json，确认旧依赖的环境要求。
3. 按上游 Usage，在根目录安装依赖，再进入具体实现目录安装该例子的依赖。
4. 使用相应目录的 `npm start` 构建资源，然后打开该目录的 `index.html`。

README 举例的目录包括 `facebook-flux` 与 `redux`。复现建议放在独立目录，不直接把它的旧依赖并入现有业务工程。

## 一个使用示例
按官方 Demo 说明，在购物界面选择几件商品并加入购物车，然后打开浏览器控制台，点击 Checkout。

预期是在控制台看到包含已选商品的载荷。接着可以在两种实现中分别追踪：按钮事件产生什么 action，哪个 store 或 reducer 更新数据，视图怎样取得新的购物车内容。

这个例子没有真实支付流程，Checkout 用于展示状态输出。本站核对了 README 的步骤，没有安装历史依赖或运行在线演示，不宣称全部实现目前都能直接启动。

## 注意事项与相关项目
README 中不少项目链接、构建工具与技术选型来自早期生态。比较时应固定同一任务、区分代码组织方式和当前维护状况，不能仅据这个例子判断大型应用的性能。理解完历史模型后，如需在新项目接入某个方案，应再查其当前官方文档。
