## 它是什么
Caddy 是可扩展的服务平台，标准构建包含 HTTP 和 TLS 模块，常用作网站服务器与反向代理。配置原生采用 JSON，也能通过 Caddyfile 等适配器表达；运行中的配置可通过管理 API 调整。

## 适合什么场景
给已有 Web 应用提供 HTTPS 入口、将请求转到后端端口，或托管静态文件。自动证书管理减少手工续期，但仍需要正确的域名解析、网络可达性、存储权限和服务运维。

## 如何开始
从官方 Releases 或安装文档取得适合平台的程序，先读 Getting Started。明确后端地址、监听端口及已有服务占用；需要额外插件时再研究 xcaddy，不必为基础反向代理自行构建。

域名自动 HTTPS 与仅监听普通 HTTP 端口是不同情况。为公网域名申请证书时，应按文档核对 DNS 与 80／443 入口；不要为了快速测试随意改系统信任或开放管理 API。

## 一个使用示例
官方入门例子，未执行：已有本机后端监听 `127.0.0.1:9000` 时，在 Caddyfile 中写入：

```caddyfile
:2080
reverse_proxy :9000
```

在该目录运行 `caddy run`，访问 `http://127.0.0.1:2080`。预期经 Caddy 转到后端；这是普通 HTTP 示例，监听 `:2080` 可能对其他网卡开放，应放在明确隔离的测试环境。改为公网域名时需另行核对 HTTPS 前提。

## 注意事项与相关项目
证书、私钥、管理接口和上游认证仍需妥善保护。客户端到 Caddy 与 Caddy 到后端是否加密应分别检查，自动 HTTPS 不等于整条链路都加密。Uptime Kuma 可从监测节点观察站点可用性，但不替代服务配置或安全审计。
