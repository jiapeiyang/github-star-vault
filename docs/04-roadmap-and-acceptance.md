# 路线图与验收标准

> 实施说明：本文件保留早期里程碑基线。可直接执行的任务拆分、React/Vite 选择和最新失败语义见 [`DEVELOPMENT_PLAN.md`](../DEVELOPMENT_PLAN.md)。

## 1. 实施原则

实现按可独立验证的纵向切片推进。每一步都能产生可审阅结果，不先搭一个庞大框架再等待功能补齐。

建议拆成四个实现批次：

1. 数据契约与同步。
2. 人工策展与 README。
3. 静态网站。
4. 自动同步、发布和完整验收。

学习回顾、AI 和在线编辑必须在 MVP 有真实使用记录后再决定。

## 2. Milestone 0：需求冻结

当前目录已经完成初始调研，进入实现前只需确认 [待确认决策](05-open-questions-and-decisions.md) 中的默认值。

完成标准：

- 公开/私有边界明确。
- “实时”SLO 明确。
- 主分类、资源类型和阶段枚举冻结为 v1。
- 仓库名、网站语言和部署目标确定。
- 明确哪些字段由 GitHub、人工和构建系统分别拥有。

## 3. Milestone 1：数据契约与同步

### 交付物

- `config/project.json` 与 `config/categories.json`。
- `scripts/sync_stars.py`。
- `scripts/verify_data.py`。
- 首次导入的 `data/repositories.json`。
- API fixtures 与必要测试。

### 必须覆盖的测试

- 多页响应完整合并。
- 第二页请求失败时不替换旧文件。
- 旧集合非空而新结果为零时拒绝发布。
- 相同 `repo_id` 改名后仍为一条记录。
- 新增项目进入当前集合。
- 旧项目缺失时标记 `missing`，不能删除人工内容。
- fork 和上游 archived 仅标记，不自动删除。
- 输出顺序稳定；同一输入重复运行不产生 diff。

### 运行验证

```bash
python3 scripts/sync_stars.py --username jiapeiyang
python3 scripts/verify_data.py data/repositories.json
git diff --exit-code data/repositories.json
```

最后一条命令用于验证第二次相同输入没有格式或排序噪声；真实上游数据发生变化时需使用固定 fixture 验证幂等性。

### 验收

- 在同一 API 快照内，活跃记录数等于完整分页读取数。
- 当前所有活跃记录 `visibility=public`。
- `repo_id` 无重复。
- 首次导入项目默认阶段可推导为 `imported`。

## 4. Milestone 2：人工策展与 README

### 交付物

- 人工 Markdown Schema 与示例。
- 构建时合并函数。
- 自动生成的 README 索引。
- 分类、类型、阶段和学习结论校验。

### 必须覆盖的测试

- 同步后人工文件字节内容不变。
- 人工文件通过 `repo_id` 关联仓库改名前后的记录。
- 未策展的历史项目默认为 `imported`，上线后新增默认为 `inbox`。
- `learned` 无 takeaway 时构建失败。
- 不存在的枚举、重复语言标签、超过 5 个标签时给出明确错误。

### 验收

人工整理 5 个真实项目，其中至少覆盖：

- 一个 AI/Agent 项目。
- 一个较早的前端项目。
- 一个上游 archived 项目。
- 一个资料合集。
- 一个只打算作为参考的项目。

生成 README 后能从分类与阶段两个入口找到这 5 个项目，重新同步不会丢失内容。

## 5. Milestone 3：Astro 静态网站

### 交付物

- 首页、项目库、详情页、关于页。
- 客户端搜索与组合筛选。
- URL 可保存筛选状态。
- 响应式布局与基础无障碍支持。

### 功能验收

在 30 秒内完成以下任务：

1. 找到“AI 与 Agent”中处于“待学习”的项目。
2. 找到前端分类中被上游作者 archived 的项目。
3. 找到最近一个月收藏的 Python AI 项目。
4. 只凭个人一句话备注找回一个记不起名称的仓库。

### 构建验证

```bash
npm ci
npm run check
npm run build
```

浏览器检查：

- 首页能看到最近新增、继续学习和最后同步时间。
- 搜索、筛选、清除和浏览器返回键行为正确。
- 仓库详情中 GitHub 事实与个人判断有明确区分。
- 手机宽度下没有横向溢出或不可操作控件。
- 控制台没有错误，所有外链可由键盘访问。

283 条数据暂不需要虚拟列表或服务端搜索。只有实际性能测量出现问题后再优化。

## 6. Milestone 4：GitHub Actions 与 Pages

### 交付物

- `site.yml`：`push`、每 6 小时 schedule、手动触发。
- 同一运行内完成同步、验证、构建和 Pages 部署。
- 页面展示最近成功检查时间与数据 commit。
- 失败时保留上一版可用网站。

### 线上验收

1. 手动触发一次 Action，确认所有分页成功、验证通过、Pages 部署成功。
2. 新 Star 一个用于测试的公开仓库，手动同步后确认它进入 `inbox`。
3. 为该项目添加人工分类与备注，重新同步后确认内容仍在。
4. 用 fixture 验证退出 Stars；若进行真实操作，确认记录退出默认视图但人工内容仍能找回。
5. 检查 Action 权限只有需要的 `contents`、`pages` 和 `id-token`。
6. 检查公开仓库、Action log、构建 artifact 中没有 PAT、Cookie 或私有仓库信息。

## 7. 上线后两周观察

MVP 上线后记录两周，不急着加 AI：

- 新 Star 数量。
- 7 天内完成整理的数量与比例。
- `queued`、`reference`、`archived` 的分布。
- 实际使用过的搜索字段和筛选组合。
- 重新打开旧项目的次数。
- 从 `learning` 进入 `learned` 的数量。
- 每次整理一个项目需要多长时间。

若整理率低，先减少必填字段或改善入口。不能先假设 AI 摘要能解决习惯问题。

## 8. 第二阶段的进入条件

| 功能 | 进入条件 |
|---|---|
| AI 分类建议 | 人工分类时间成为明确瓶颈，且已有至少 50 条人工标签可作为评估样本 |
| 语义搜索 | 多次出现关键词和标签都无法找回项目的真实案例 |
| Pagefind | 详情页或长笔记数量使浏览器端索引产生可测量性能问题 |
| 在线编辑 | Git 文件编辑真实阻碍每周整理，而不是还未形成整理习惯 |
| 浏览器扩展 | 6 小时同步或 Star 后补充原因的延迟反复造成遗漏 |
| 私有数据层 | 确认有需要管理但不能公开的 Stars 或笔记，并能接受单独部署与凭证管理 |

## 9. 风险与处理

| 风险 | 最坏影响 | 频率 | 等级 | MVP 处理 |
|---|---|---|---|---|
| 分页中途失败仍覆盖旧数据 | 大量项目被误标缺失 | 未知 | A | 全部页成功并校验后才替换与发布 |
| 非空列表异常变空 | 网站项目库被清空 | 未知 | A | 零结果保护，要求人工确认 |
| 生成器覆盖人工内容 | 个人分类和学习笔记丢失 | 未知 | A | 目录与字段所有权隔离，测试字节不变 |
| 定时任务延迟或偶发失败 | 更新晚于 6 小时 | 未知 | B | 保留旧站与手动触发，不加重试队列 |
| 两个 workflow 同时提交 | 一次 push 失败 | 未知 | B | 不加锁，下次或手动运行恢复 |
| AI 误分类 | 检索结果不可信 | 未知 | B | MVP 不自动应用 AI 结果 |
| 私有数据出现在公开站 | 信息泄露 | 未知 | A | 公共端点、public 断言与构建检查 |

## 10. 本阶段明确不防

- 不为定时任务偶发延迟加重试、锁、队列或备用调度器。
- 不为 GitHub API 三页请求实现 ETag 缓存。
- 不为数百条数据提前加入虚拟列表、服务端搜索或数据库。
- 不处理“用户有意把公开 Stars 全部清空”的自动流程；零结果需要显式人工操作。
- 不保证精确的取消 Star 时间，只记录系统发现缺失的时间。
