## 最值得先讨论的四项

### 1. 这是公开知识库，还是私人工作台

推荐公开知识库。它与“展示这些仓库内容”的原始目标一致，也让技术方案保持纯静态。

如果个人学习笔记会包含公司项目、内部判断或敏感链接，就需要拆成公开策展和私人笔记两层。这个决定会改变数据目录、构建过滤、部署权限和验证强度，应在写代码前明确。

### 2. “实时”到底希望多快

推荐 6 小时 SLO。你在 2026-09-04 约 5 分钟内连续新增了两个 Star，说明自动化确实有价值，但用户通常不需要在点击 Star 后几秒打开目录站。

可选口径：

- 6 小时：推荐 MVP。
- 1 小时：仍然简单，只增加 Actions 运行频率。
- 秒级或分钟级：需要浏览器扩展、常驻服务或额外交互，不建议先做。

### 3. 分类是“领域”还是“技术语言”

推荐领域为主分类，语言为筛选项。一个 Python 项目可能是 Agent 框架、视频工具、金融分析或教程，按语言分组不能说明它为什么值得学习。

建议先用八类跑最近 50 个项目，记录无法稳定归类的案例，再冻结 v1。不要为了追求一次到位增加十几类。

### 4. 网站首先服务自己还是公开读者

推荐先服务自己。首页优先展示收件箱、继续学习和随机重访，而不是营销式 Hero 或热门榜单。公开读者仍能使用项目库与分类页，但不能反过来挤压个人学习流程。

## 已形成的产品判断

这些结论有当前数据和调研支撑，除非目标变化，不建议反复打开：

- GitHub 仍是唯一收藏入口，不另做收藏表单。
- 使用 `repo_id`，不使用 `owner/name` 作为主键。
- 每次完整对账，不做两套增量/全量同步模式。
- 自动数据与人工数据物理分开。
- 网站从同一份 Git 数据构建，不另建数据库。
- GitHub Lists 可作为未来出口，不作为 MVP 真源。
- 机器建议不能覆盖人工结论。
- 上游 archived 与个人 archived 必须分开。
