#### 这次为什么值得翻开它

Map-of-Javascript 的价值在于把散落的概念放回同一张图。遇到“明明写在前面，为什么后执行”时，可以拿它定位概念，再用规范确认图中省略的条件。本期只沿着 **同步代码 → Promise 回调 → 微任务 → 下一个任务** 读一小段，先不试图读完整张地图。

从[仓库的原图入口](https://github.com/mechaniac/Map-of-Javascript/blob/main/Javascript_01.jpg)开始，放大自己需要的区域。图是索引；执行边界以 [MDN 的微任务说明](https://developer.mozilla.org/en-US/docs/Web/API/HTML_DOM_API/Microtask_guide)和 [HTML 事件循环规范](https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model)为依据。

#### 先推一下，这五条日志会怎样排列

下面是本站编写的说明性代码，不是上游项目示例。先分别标出同步语句、微任务和定时器回调，再看后面的推理。

```js
console.log("A：同步开始");
setTimeout(() => console.log("B：定时器"), 0);
Promise.resolve().then(() => {
  console.log("C：Promise 回调");
  queueMicrotask(() => console.log("D：追加的微任务"));
});
console.log("E：同步结束");
```

#### 顺序背后的三个判断

预期顺序是 **A → E → C → D → B**。

1. 先运行当前同步代码，所以 A 和 E 连在一起。`setTimeout(..., 0)` 不会中断正在执行的代码。
2. 在这里的微任务检查点，已入队的 Promise 回调运行，输出 C；它又加入一个微任务，继续输出 D。
3. 本轮微任务队列清空后，才轮到这个例子里的定时器任务 B。这里没有比较不同任务源的排序，也没有推断所有浏览器活动的完整时序。

反过来想：如果把 D 改成另一个定时器，它就不再是“本轮继续排空的微任务”。关注它进入哪种队列，比只记住这五个字母更有用。

#### 回到页面：日志顺序不等于画面顺序

上面的日志不能证明浏览器已经绘制了画面。把工作移进 Promise 回调，也不意味着它会自动让出时间供页面绘制；不断追加微任务可能推迟后续任务。涉及绘制时机，需要另外观察渲染机会，不能仅凭“异步”两个字判断。

BetterScroll 提供一个更具体的检查点：图片未加载完时，内容高度可能还没有达到最终值。此时应观察图片加载完成，再按官方文档刷新尺寸。**等代码回调执行、等资源就绪、重新测量尺寸，是三个不同的判断。**

#### 本页的验证边界

本页代码已在 Node.js 和 Codex 内置浏览器的独立页面中原样执行，均输出 **A → E → C → D → B**。这只验证了本例的日志顺序。其余部分依据上方公开资料整理；没有运行 Map-of-Javascript 仓库脚本、fe-interview 题库或 BetterScroll，也没有测量绘制和真机滚动性能。导读有独立核查日期，可以后续更新；第 001 期的名单和入选理由保持原样。
